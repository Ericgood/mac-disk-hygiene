# 05 多会话 / 多 Agent 协作清理

一台机器上同时有十几个 AI 编程会话时，「这个目录还要不要」只有负责它的那个会话最清楚。清理会话不应该替别人做判断，而应该：**给规则、让负责人自己核对、自己收、回报结果。**

## 1. 流程

1. **只读盘点**：清理会话列出所有候选（路径、大小、分支、最后活动时间、初查结论），按负责的会话 / 项目分组。
2. **初查只做参考**：用 [04](04-git-worktree.md) 的 6 条规则做一次客观初查，把结论标成「初查无阻挡」或「有阻挡项，需核对」，**不要写成「可删 / 不可删」**，避免对方照抄。
3. **发核对清单**：每个负责会话一份，用 [`templates/worktree-review-checklist.md`](../templates/worktree-review-checklist.md) 模板，写清规则、允许的收法、回复格式。
4. **负责会话自己收**：在不打断手头任务的前提下，逐项核对，用允许的方式收。
5. **清理会话核验**：对方回报后，核对路径确实已不存在、分支仍在、`df` 有对应变化。

## 2. 消息要写清楚的几件事

- 为什么找它（磁盘只剩多少、它名下有多少）；
- **不急，先把手上这一轮做完，不要打断进行中的任务**；
- 只做只读核对 + 收副本，不构建、不装依赖、不提交、不推送、不发布；
- 不确定就保留；
- 回复格式：每项「编号 已收/保留 + 一句理由」，最后一句「共收掉 X 个，约 Y GB」。

## 3. 「送达」不等于「执行了」

跨会话消息工具显示 `delivered`，只代表消息进了对方的会话，不代表对方处理了。实际遇到过：消息以「后台已处理过，不要重复执行」的摘要形式注入，对方于是回复「已后台处理，本轮不重复执行」，实际什么都没做。

**正确做法**：

- 发完后只读查看对方会话记录的最后几条，确认对方真的开始处理（例如开始读清单、跑 `git status`）；
- 如果对方回「已在后台处理」，但看不到任何结果，就认定**没执行**；
- 这时把可以直接粘贴的原文交给用户，由用户在对应 App 里手动发送，并在开头写明「之前通过 xxx 发给你的请求其实没有执行，请现在处理」。

## 4. 老会话被归档时

长对话换新时，旧会话常被改名「归档」，发给它的请求就不会再有人回。发消息前先确认：这个项目**当前**负责的是哪个会话。

## 5. 不要让别人替你越权

如果清理会话自己被拒绝了某个操作（比如没权限删某个目录），不能转头让另一个会话去做。这等于绕过了用户的权限决定。被拒的事情交回给用户。
